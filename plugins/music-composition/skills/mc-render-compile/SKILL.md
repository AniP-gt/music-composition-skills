# コンパイル層（Render Compile）

**このライブラリのコンパイラは1つ。バックエンドはデータとして定義する。**

```
ARR-SPEC（唯一のIR）
    ↓  mc-render-compile   ← この1つが共通処理を担当
    ├─→ backends.yaml: yue2      ★ ABC楽譜を直接受け取れ、制御性が最も高い
    ├─→ backends.yaml: suno         自然文のprompt＋セクションタグ。仕上がりが最も洗練されている
    ├─→ backends.yaml: minimax-music-3
    ├─→ backends.yaml: ace-step-1.5
    ├─→ backends.yaml: stable-audio-3   （ボーカルなし）
    └─→ backends.yaml: symbolic         MIDI/MusicXML、完全に決定的
```

> **新しいモデルを追加するには、`backends.yaml` にブロックを1つ足せばよい。スキルの変更は不要。**
> コンパイラのフロントエンドとバックエンドを分離する設計と同じ考え方。

## 3. ★ コンパイルの順序

**順番どおりに進める。手順を飛ばすと、「プロンプト内の指示が食い違う」ことがある。**

| # | 手順 | 説明 |
|---|---|---|
| **0** | **`mc-workflow` §3.0の20項目で自己点検する** | 満たさない項目は直すか理由を書いてからコンパイルする。**コンパイルの可否を決める基準ではなく**、仕様の書き漏れを見つける最後の機会 |
| **1** | **`backends.yaml` の `honors` を読む** | `none` のフィールドに印を付ける。**プロンプトと採点の両方から外す** |
| **2** | **`mix_intent.mood` を最初に置く** | ほかの判断に優先するため、プロンプトの先頭付近に置く |
| **3** | **style_promptをコンパイルする** | §4 |
| **4** | **セクションタグの列をコンパイルする** | §5。★ **タグ数は `form` のセクション数と一致させる**（lint #13） |
| **5** | **歌詞のブロックをコンパイルする** | §5.3 |
| **6** | **記号出力の経路を使う**（バックエンドが対応する場合） | → `mc-symbolic-score` |
| **7** | **exclude／ネガティブプロンプトをコンパイルする** | §4.4 |
| **8** | **シードとバッチの規模を決める** | §7.3 |
| **9** | **`render.<backend>` に書き戻す** | 今回のコンパイル結果をARR-SPEC自体に記録する |

★ **手順9を忘れない**。`render` ブロックも仕様の一部であり、
**書き戻しておかないと、次のABテストで前回の入力内容を確認できない。**

## 4. style_promptで構造化フィールドを情報を落とさず自然文にまとめる

### 4.1 情報源の優先順位

**以下のフィールドから情報を取り出し、この順に並べる**（前にあるほどモデルが採用しやすい）。

1. `mix_intent.mood`（1文）
2. `meta.style_layer` に対応するスタイルの語彙（→ L3スキル）
3. `meta.tempo`、`meta.key`
4. `arrangement.roster[].instrument` ＋ `timbre`
5. `groove.feel` ＋ push_pullの**方向**（ミリ秒表記を避け、"bass playing ahead of the beat"と書く）
6. `vocal.persona` ＋ `vocal.delivery`
7. 時代や制作上の質感を表す語

### 4.2 ★ 3つの厳守事項

1. **情報を持たない形容詞は禁止**。`epic` / `emotional` / `beautiful` / `amazing` / `masterpiece` / `perfect`
   （lint #13で警告）。実行できる指示を一切含まず、プロンプトの枠を消費する
2. **数値を聴感で分かる記述に変換する**
   `push_pull: bass −12ms` → `bass playing slightly ahead of the beat`（**−12msと書かない**）
3. **すべての語がrosterの項目かspecのフィールドに対応するようにする**。
   ★ **自己点検**。style_promptの語を一つずつ囲んで出所を確認し、出所が分からない語を削る

### 4.3 実測例（City Pop）

```
1980s Japanese city pop, 112 BPM, D major, Rhodes electric piano,
16th-note muted clean guitar, electric bass playing ahead of the beat,
gated reverb snare, analog saw synth lead riff,
tenor saxophone solo in the bridge and outro,
female vocal with breathy tone mixed back, warm tape saturation
```

**記述の順番に注目**。時代＋スタイル → テンポと調性 → **楽器ごとに奏法を併記** → ボーカル → 制作上の質感。
**どの形容詞にも具体的な情報がある。**

### 4.4 exclude（ネガティブプロンプト）

**「この曲に含めない要素」を具体的に書く**。「耳障りにしない」のような曖昧な指示を避ける。

実測例：
```
["EDM drop", "trap hi-hats", "modern sidechain pumping",
 "orchestral epic", "fade out ending"]
```

★ 最後の `fade out ending` に注意。
**フェードアウトは生成モデルのデフォルトの終わり方**なので、除外しなければ必ずフェードアウトする
（→ `mc-arrangement-arch` §8 3つの終わり方）。

## 5. セクションタグと歌詞

### 5.1 対応表

`form[].name` → バックエンドのタグ：

| ARR-SPEC | Suno / 多くのバックエンド |
|---|---|
| Intro | `[Intro]` |
| Verse | `[Verse]` |
| Pre-Chorus | `[Pre-Chorus]` |
| Chorus | `[Chorus]` |
| **Bridge** | `[Bridge]` |
| Instrumental | `[Instrumental]` |
| Outro | `[Outro]` |

★ **タグの対応で間違えやすい2点**。
1. **大サビには `[Bridge]` を割り当て、`[Chorus]` は使わない**（→ `mc-form` §7）。
   対応を誤ると、内省的な展開にしたい箇所でバックエンドが勢いのあるサビを生成する
2. **落ちサビ（編成を薄くしたサビ）にも `[Chorus]` を割り当てる**。
   編成を薄くする指示はstyle_promptかセクションの注記に書き、**タグはそのまま使う**

### 5.2 タグ数とセクション数を一致させる

規則の全文は§3の手順4（タグ数は `form` のセクション数に一致させる。lint #13）を参照。§11の必須チェックリストにも記載している。コンパイル時に特に間違いやすいため、独立した節を設けている。歌詞のセクションを手作業で変更すると、タグの追加や削除を忘れやすい。タグが1つ足りないだけでも、バックエンドは該当セクションの種類を自分で決める。問題が出たら、まずここを確認する。

### 5.3 歌詞をブロックに分ける

- 歌詞をセクションごとに分け、**タグと1対1で対応させる**
- ★ セクション内の改行は**フレーズの区切りに影響する**。バックエンドは改行を見た目の整形だけでなく、音楽上のフレーズ境界として読む
- **歌詞の参照元**。このスキルがコンパイルするのは、このパッケージ側の項目（セクションタグ、スタイル記述、除外語、記号出力の経路）。歌詞は `meta.upstream.lyrics.sections` から読み込む。そこにある `id` は `form[].id` と同じなので、idに従い、各セクションの行を対応するタグの下に置く。同じ曲の歌詞仕様書を参照してもよい。`meta.upstream.lyrics.source` で探し、セクションidで行を取り出す。語句や改行を変えず、行をそのまま使う
- セクションidが一致しない場合（歌詞に `form` にないセクションがある、またはその逆）→ 推測せず `form[]` に従ってコンパイルし、対応しないセクションを `checks.exemptions` に記録する。さらに `messages` に作詞担当への連絡を1件書く（`to: lyrics`）。歌詞を先に書く場合、セクションidは歌詞側が決める（`mc-workflow` §5.1）ので、このパッケージの `form[]` を修正してそろえる
- 歌詞がない場合は `mc-workflow` §2.3の3つのケースに従う（歌詞を付けない、仮の音節でボーカルのリズムを示す、このパッケージで歌詞を書いて例外を記録する）
- 分けたブロックをバックエンドに渡すときの形式（改行の影響、息継ぎ、音の引き伸ばし、句読点と括弧、歌詞欄に注記を入れないこと、インストゥルメンタルのセクション、歌詞を受け取れるバックエンド、受け渡し前の確認項目）は[reference-lyrics.md](reference-lyrics.md)を参照

## 6. ★ honors の契約：このスキルで最も重要なルール

各バックエンドは `backends.yaml` で、ARR-SPEC の各フィールドをどの程度実行できるかを宣言する。

| 値 | 意味 | 検収時の扱い |
|---|---|---|
| **exact** | 正確に実行できる | **採点対象**。基準を満たさなければ実行できなかったと判断する |
| **hint** | ヒントとして生成に影響を与えられる | **採点対象だが、重みを下げる** |
| **none** | そのフィールドを受け付けない | ★ **採点対象外**とし、「このバックエンドは非対応」と明記する |

### 6.1 none を 0 点にせず、採点対象外にする理由

> **Suno には正確なコードがそもそも伝わっていない。「コードどおりに生成できていない」と減点すれば、対応できないことを理由に罰することになる。**

★ **さらに重大な問題**は、none を 0 点にすると、
**「音像の定位には対応できない」と正直に申告したバックエンドが、対応できると装ったバックエンドより低い点を取る**ことだ。
採点方式が対応能力の虚偽申告を有利にしてしまう。**採点基準の解釈の違いでは済まない、正しさに関わるバグだ。**

### 6.2 コンパイル時の使い方

1. `none` のフィールドは**プロンプトに入れない**。書いても効果がなく、有用な情報に割ける余地が減る
2. `hint` のフィールドは**記述するが、実行を当てにしない**。best-of-N と組み合わせる
3. `exact` のフィールドは**必ず正確に記述する**。ここで費用に見合った制御が得られる

## 7. 対応能力に応じた指定の緩和

### 7.1 1 つの仕様を複数のバックエンドで使う

**バックエンドごとに仕様を作らない。** 仕様は 1 つとし、honors に応じて指定を緩和する。

| フィールド | YuE2 (exact) | Suno (none) | 指定の緩和方法 |
|---|---|---|---|
| `form.harmony` | ABC にコンパイル | — | **スタイル記述で旋法や響きの傾向を示す語に置き換える**（「サブドミナントマイナーの響きを多用する」） |
| `form.bars` | ABC の小節にコンパイル | — | **曲のセクションのタグ列で長さをほのめかす**にとどめ、指定どおりの小節数にはできないことを受け入れる |
| `groove.push_pull` | — | hint | "playing ahead of the beat" に置き換える |
| `mix_intent` | none | none | ★ **どちらも非対応 → 後処理するか、記号表現を経由する** |

### 7.2 緩和した指定を記録する

記録形式は §10（`checks.exemptions` に記入）、納品項目は §8.1（`render.<backend>` に書き戻す）を参照。★ 今回どのフィールドの指定を緩和したかを `render.<backend>` に残す。そうしないと、次回に仕様準拠率が低かったとき、仕様の書き方が悪かったのか、バックエンドがそもそも対応できなかったのかを判別できない。どちらの場合も仕様準拠率は同じように下がり、その違いはコンパイルした時点でしか把握できないため、その場で記録する。

### 7.3 シードとバッチ生成

| 目的 | 方法 |
|---|---|
| **AB 比較** | **シードを固定し**、変更するフィールドを 1 つに絞る。2 つ変えると差の原因を特定できない |
| **完成品の作成** | **best-of-N**（YuE2 では 8 を推奨）で生成し、仕様準拠率で並べる（計測ツールがあれば算出し、なければフィールドごとに照合する）。**その後、上位 3 件を聴いて選ぶ** |
| **探索** | シードは固定せず、どのシードで何が生成されたかを記録する |

## 8. バックエンドに渡して実行する

このスキルの出力は**各バックエンドに渡す入力値**である。Suno にはスタイル記述と曲のセクションのタグ、YuE2 には ABC とパラメータ、
ACE-Step / MiniMax / Stable Audio には prompt とパラメータを用意する。
★ **これらの値をどのツールでモデルに渡すかはユーザーの環境で決まる**。コマンドライン、Python API、
ComfyUI のようなノードベースの環境のいずれも使える。このスキルでは実行環境を前提に置かず、管理もしない。
`backends.yaml` の `transport` は「このバックエンドを通常どこで実行するか」を示す参考情報であり、実行の前提条件にはしない。

### 8.1 ユーザーに渡すもの

| バックエンド | 渡すもの |
|---|---|
| Suno | style_prompt、exclude、曲のセクションのタグ付きの歌詞または仮の音節（§4、§5） |
| YuE2 | ABC テキスト（`mc-symbolic-score`）＋ genre / tempo パラメータ。**モデル自身による記号表現の計画を省き、この ABC を音声合成工程に直接渡すことも明記する** |
| ACE-Step / MiniMax / Stable Audio | prompt と長さなどのパラメータ。各バックエンドの `accepts` リストに従う |

各項目を `render.<backend>` に書き戻す。ユーザーはその値を自分のツールに入力すればよい。

### 8.2 YuE2 への接続で重要な点

YuE2 は 2 段階で動く。**記号表現の計画（モデル自身が ABC を書く）→ ABC から音声を合成する**。
★ **第 1 段階を迂回し**、`mc-symbolic-score` でコンパイルした ABC を第 2 段階に直接渡す。
ここでこのリポジトリの制御力を最大限に発揮できる。仕様が「ヒント」を超えて、そのまま実行される。
YuE2 に対応する環境ならこのつなぎ方ができる（公式リポジトリにはスクリプト、ComfyUI にはネイティブノードがある）。具体的な接続方法はユーザーの環境による。

> YuE2 の公式リポジトリには `skills/yue2-music/` が付属する（「音楽上の不変条件のチェック」を含む）。
> ★ **これを書き直さない**。ここでは ARR-SPEC→ABC のアダプターだけを書き、モデルの操作方法は公式のスキルを参照する。

## 9. 新しいバックエンドを追加する

1. `backends.yaml` にブロックを追加する。項目は `id / name / transport / accepts / honors / license`
2. ★ **`honors` は実際の対応能力どおりに記入する**。対応できないなら、体裁を整えるために `hint` とせず `none` と記入する（理由は §6.1 を参照）
3. `transport`（hosted / local）を記入する。通常の実行環境を記録する項目であり、必須の実行条件ではない
4. **`example-01-citypop.yaml` を一度実行し**、コンパイル結果が妥当か確認する
5. **スキルは一切変更しない**

## 11. コンパイル後の必須チェック

- [ ] `mc-workflow` §3.0 の 20 項目を確認し、満たさなかった項目には理由を書いた
- [ ] 対象バックエンドの `honors` を確認し、`none` のフィールドは**プロンプトに入れていない**
- [ ] `mood` はプロンプトの**前方に置いた**
- [ ] style_prompt の**すべての語が仕様のいずれかのフィールドに対応している**
- [ ] **`epic`/`emotional`/`beautiful` のような具体性に欠ける語がない**
- [ ] 数値パラメータを**聴感で分かる記述に変換し**、プロンプトにミリ秒を書いていない
- [ ] 曲のセクションのタグの**数 == `form` のセクション数**
