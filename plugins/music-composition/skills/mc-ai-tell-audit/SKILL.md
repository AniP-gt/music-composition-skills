# AIっぽさの診断（AI-Tell Audit）

**生成結果は1件ずつ、このスキルで最終チェックする。**

> **AIらしさは具体的な特徴から判定できる。**
> **生成モデルは仕様に指定がなければ既定のパターンに従う。そのパターンは列挙できる。**
> このスキルでは、各パターンの確認方法と担当スキルを示す。

## 作業別の参照先

| 作業 | 参照先 |
|---|---|
| 生成直後の受け入れ判定 | §2 の14項目 → §3 の判定 |
| 「AIっぽく聞こえるが、どこがそうなのかわからない」 | §2（★ **直感に頼らず1項目ずつ確認する**） |
| 仕様遵守率が高いのに結果が悪い | §4 |
| 閾値を決める | §3.2 ゼロ点の校正 |
| 見つかった問題を修正する | §5 修正手順 |
| ボーカルの4項目を確認する | §6 |

## 担当範囲

| 項目 | 参照先 |
|---|---|
| 仕様を**書き終えた時点**での確認 | `mc-workflow` §3.0 の20項目のセルフチェック |
| 仕様遵守率の算出 | このスキルの §3.1（定義と算出基準）。honors の3段階が採点に与える影響は `mc-render-compile` §6 を参照 |
| 具体的な修正方法 | 各 L1/L2 スキル（参照先は §5） |
| バックエンドが対応できないフィールドの扱い | `mc-render-compile` §6、§7 |

> ★ **20項目のセルフチェックとの分担**
> **セルフチェックでは仕様を書き切ったか、このスキルでは生成結果が人の手で作ったように聞こえるかを確認する。**
> **両方を確認して完了。** 17項目すべてを通過した仕様でも、AIらしさが目立つ音源が生成されることはある。

## 2. ★ 14項目のチェックリスト

**全体の印象に頼らず、該当する項目を一つずつチェックする。**

| # | AIらしさの原因（バックエンドの既定の挙動） | 対応する spec フィールド | 自動測定 | 担当 |
|---|---|---|---|---|
| **1** | すべてのセクションの小節数が 8 の整数倍 | `form[].bars` | ✅ セクション境界の検出 | `mc-arrangement-arch` §4 |
| **2** | **エネルギー曲線が単調に増加し、一度も下がらない** | `energy_curve`、`subtraction_events` | ✅ セクションごとの RMS | `mc-arrangement-arch` §2、§3 |
| **3** | 編成が最初から最後まで変わらない | `roster[].entry/exit` | ✅ 分離したトラックごとの onset 密度 | `mc-arrangement-arch` §5 |
| **4** | 曲全体が同じコード進行の繰り返し | bridge で必ず一時的に調を外れるか、転調する | ✅ コード認識 | `mc-harmony`、`mc-modulation` |
| **5** | fill が毎回決まって 4 の倍数の位置に入る | `fill_policy` | ✅ onset のピーク位置 | `mc-rhythm-section` §8 |
| **6** | ボーカル以外に耳に残るフックがない | `hooks.arrangement_hook` | ⚠️ 半自動（繰り返すセクション間の類似度） | `mc-arrangement-arch` §7 |
| **7** | **ダイナミクスがつぶれ、スペクトル重心が一定** | `dynamics`、`width_map` | ✅ DR／LRA、スペクトル重心の時系列分散 | `mc-mix-intent` |
| **8** | **グリッドに揃い、push/pull がない** | `groove.push_pull` | ✅ グリッドに対する onset のずれ | `mc-rhythm-section` §3 |
| **9** | 長さがいつも 3:30 で、終わりに余韻がない | `target_duration` ＋ エンディングの処理 | ✅ | `mc-arrangement-arch` §8 |
| **10** | **どのフレーズも強弱や発音が同じで、息混じりの声、声の裏返り、rubato がない** | `vocal.delivery`、`dynamics_by_section` | ⚠️ ステム分離後に短時間ラウドネスの分散を測る | `mc-vocal-direction` §2、§4 |
| **11** | **サビを3回ともまったく同じように歌う** | `vocal.chorus_variation` | ✅ ボーカルトラックのセクション間の類似度 | `mc-vocal-direction` §1④ |
| **12** | **息継ぎの位置が不自然、または息継ぎが聞こえない** | `vocal.breath_points` | ⚠️ 半自動 | `mc-vocal-direction` |
| **13** | **ad-lib が均等に入るか、まったくない** | `vocal.ad_libs` | ⚠️ 半自動 | `mc-vocal-direction` |
| **14** | **すべての音程がぴったり合っている** | `vocal.pitch_policy` | ⚠️ 半自動（ステム分離後に音高のずれの分布を測る） | `mc-vocal-direction` §4 |

> ★ **この表には3つの用途がある**。このスキルとAB実験の評価表の骨格であり、20項目のセルフチェックの根拠でもある。
> **変更したら3か所すべてに反映する。**

### 2.1 ★ 見落としやすく、影響の大きい3項目

**耳障りに聞こえるとは限らず、人が作ったように聞こえないという形で現れるため、見落としやすい。**

| # | 影響が大きい理由 |
|---|---|
| **2（エネルギーが上がる一方）** | 実測では実際の編曲 **62/62** にエネルギーが下がる箇所があった。**検出率が最も高い強いルール**で、聴感でも最もAIらしさが目立つ |
| **8（すべてグリッドに揃っている）** | 実測では **62/62**。判定するのは「**曲全体で全楽器がグリッドに揃っているか**」。ドラムセットの完全クオンタイズは許容する（→ `mc-rhythm-section` §2.0） |
| **6（ボーカル以外に耳に残るフックがない）** | 「悪くないが印象に残らない」という形で現れ、**ほかのチェックをすべて通りやすい**。このフックがないと、曲を聴き終えたそばから忘れてしまう |

## 3. 2つの指標は合算しない

### 3.1 定義

| | 評価するもの | 算出方法 | 範囲 |
|---|---|---|---|
| **仕様遵守率** | **バックエンドが仕様をどれだけ反映したか** | フィールドごとに仕様と照合する | 0–100 |
| **AIらしさの該当数** | **完成音源に生成モデル特有の特徴がいくつあるか** | このスキルの §2 を1項目ずつ確認する | 0–14 |

★ **2つの指標は必ず別々に扱う。** 組み合わせによって原因を診断できる。

```
仕様遵守率が高い ＋ 該当数が少ない → 良好。採用
仕様遵守率が高い ＋ 該当数が多い   → ★ 仕様そのものにAIらしさがある（§4 参照）
仕様遵守率が低い ＋ 該当数が少ない → バックエンドの独自の判断で良い結果が出たが、再現できない（§4.2 参照）
仕様遵守率が低い ＋ 該当数が多い   → コンパイルまたはバックエンドの選択に問題がある。mc-render-compile に戻る
```

### 3.2 ★ ゼロ点の校正：合格の目安が 60 ではなく 82 の理由

**仕様と無関係でも、制作の質が高い完成曲は仕様遵守率の採点表で 63–66 点を取る。**

通常の曲ならどれも、テンポやセクション、ダイナミクスがあるなど、一部の項目を偶然満たすためだ。

| 基準 | 値 |
|---|---|
| **ゼロ点**（仕様と無関係な完成曲） | **63–66** |
| **及第** | **70** |
| **合格** | **82** |

★ この3つは**参考値**。ゼロ点は、City Pop の仕様（112 BPM、10セクション、114小節）と、その仕様に無関係で制作の質が高い中国語の完成曲3曲を比較し、フィールドごとに重み付けして採点した結果（63.4–66.4。同じ仕様に対して、MIDIをレンダリングしただけのデモを採点すると 39.5）。数値の水準を把握するための目安で、納品の閾値には用いない。仕様遵守率は、各フィールドを照合したうえでの判断を表す。

★★ **過去に起きた問題**。**判別力のある**項目（`boundaries`）から
**判別力のない**項目（`energy_shape`。無関係な曲でも 0.8 を取れる）へ重みを移すと、
ゼロ点の基準値（66→72）を含め、**全体のスコアが上がってしまう**。
**判別力がある項目に重みを付ける。**

### 3.3 バックエンドが対応できない項目は採点対象外

`honors: none` のフィールドは、**0点を付けずに採点から除外する**。
詳しくは `mc-render-compile` §6.1 を参照。**正しく採点するために必要な処理であり、集計方式の好みで決めるものではない。**

## 4. ★ 仕様遵守率が高いのにAIっぽく聞こえる

**これを見抜くことが、このスキルの主な目的。**

仕様遵守率が測るのはバックエンドが仕様に従った度合いであり、**仕様自体の質は評価しない**。
AIらしさのある仕様をバックエンドが忠実に実行すれば、仕様遵守率 95 でもAIっぽい曲になる。

### 4.1 仕様にAIらしさがある4つの兆候

| 兆候 | 確認する箇所 |
|---|---|
| `intent.one_thing` を**lint に通すためだけに埋めており**、読み上げると人が話す言葉として不自然 | `mc-workflow` §1 の S0 |
| `reference_pair` の `borrow` が漠然としている（「雰囲気を借りる」） | 同上。**「イントロの音数の少なさだけを借りる」まで具体化する** |
| 各セクションの `bars` に**8 の倍数を避けるためだけに**不自然な小節数を選んでいる | `mc-arrangement-arch` §4。**非対称にするなら理由が要る** |
| コード進行や転調が**定型パターンの注意基準**に該当し、採用理由が書かれていない | `mc-progressions` §3、`mc-modulation` §6 |

★ **共通点**は、**ルールを満たすことが目的になり、曲に合わせた判断が抜けている**こと。
この**人による選択の不在**が、AIらしさの定義に当たる。

### 4.2 仕様遵守率が低いが、聴き心地は良い

**バックエンドの独自の判断で良い結果が出た。完成音源を採用する場合は、次の点を把握しておく。**

- その音源を**再現できない**
- どの判断が良い結果につながったか**わからない**
- 次の曲でも一から偶然に頼ることになる

★ **対処方法**。完成音源から各フィールドを逆算して実測版の ARR-SPEC を作る。聴きながら記入し、正確に測れない項目には「概算」と付ける。
**元の仕様とどこが違うかを確認し、その差分を次の仕様作りに生かす。**

## 5. 修正手順

**直感で手順を飛ばさず、次の順に確認する。**

```
「AIっぽく」聞こえる
 └─ ① 各フィールドを仕様と照合し、仕様遵守率を出す
 └─ ② §2 の14項目を順に確認し、該当数を数える
     ├─ 仕様遵守率が低い → honors を確認
     │   ├─ このバックエンドでは該当フィールドが none → 対応範囲外。バックエンドを変える（YuE2 が最も制御しやすい）か、結果を採用する
     │   └─ none 以外 → コンパイルの問題 → mc-render-compile §3
     └─ 仕様遵守率が高いが該当数が多い → ★ 仕様そのものの問題 → §4.1
```

### 5.1 症状 → スキル（早見表）

| 症状 | 最初に確認する箇所 |
|---|---|
| 平坦で起伏がない | `mc-arrangement-arch` §2 |
| 音がぼやけて濁る | `mc-texture-layering` §4（★ **ドラムを疑う前に持続音を確認する**） |
| 主役が際立たない | `mc-texture-layering` §3 の奥行きを作る4つの手がかり |
| 機械的で正確すぎる | `mc-rhythm-section` §2 ＋ `mc-vocal-direction` §4 |
| 悪くないが印象に残らない | `mc-arrangement-arch` §7（`arrangement_hook` が空か確認） |
| 2回目のサビが1回目と同じ | `mc-arrangement-arch` §6 ＋ `mc-vocal-direction` §1④ |
| ボーカルが伴奏に埋もれる | **まず音程を確認**（`mc-vocal-direction` §4.1）し、次に周波数帯域を調べる |
| スマートフォンでベースが聞こえなくなる | `mc-sound-design` §6 の差音 |
| エンディングが唐突 / フェードアウトに問題がある | `mc-arrangement-arch` §8。★ `exclude` で `fade out ending` を除外しているか確認 |
| 技術的には整っているが、狙った感情が伝わらない | `mc-mix-intent` §3.1（`mood` の記入漏れを確認） |
| 同じコード進行が最後まで続く | `mc-harmony` §7、`mc-modulation` |

## 6. ボーカルの4項目（#10、#12、#13、#14）

**この4項目は、先にボーカルトラックを分離してから確認する。**

### 6.1 ステム分離

任意のツールでボーカルトラックを分離する。demucs などのほか、利用中の生成環境に組み込まれた分離機能を使ってもよい。一般的にはボーカル、ベース、ドラム、その他に分かれる。
このスキルではツールを指定しない。

> ★ **このライブラリでステム分離が必要になる数少ない場面の一つ**。
> マルチトラックのコーパス（Cambridge-MT）には「Suno が歌ったボーカル」がないため、生成結果から分離する。

### 6.2 ステム分離後の測定項目

| # | 測定項目 | 判定基準 |
|---|---|---|
| **10** 強弱 | ボーカルトラックの**短時間ラウドネスの分散** | 分散が 0 に近い = 全編で強弱が一定 |
| **11** サビの類似 | 各回のサビのボーカルトラックの**セクション間の類似度** | 類似度が高すぎる = そのままコピーされている |
| **12** 息継ぎ | フレーズ間でエネルギーが低い区間 | ⚠️ 半自動。現時点では耳で判定 |
| **13** ad-lib | 装飾的な発声の分布 | ⚠️ 半自動。**均等に並ぶ = 歌い回しに合わせず機械的に配置されている** |
| **14** 音程 | **音高のずれの分布** | ⚠️ 半自動。**すべて ±5 セント以内 = 過度に補正されたか、生成された歌唱** |

### 6.3 ⚠ 現状

**#12、#13、#14 は意図的に耳で判定する。**

この3項目では、息継ぎでエネルギーが下がる箇所、装飾音の分布、音高のずれの分布を調べる。自動判定するには生成モデルごとに閾値を校正する必要がある。モデルによって基準値が大きく異なるため、同じ数値を当てはめると、良い歌唱まで問題ありと判定しかねない。この3項目は耳で聴けばすぐに確認でき、機械より人の耳が細かな違いを捉えやすいため、追加の負担にもなりにくい。

## 7. 受け入れチェックリスト

**生成結果はすべて1件ずつ確認する。**

- [ ] **仕様のバージョンとシード**を記録した
- [ ] 各フィールドを仕様と照合し、仕様遵守率を把握した
- [ ] §2 の14項目を**一つずつ**確認し、印象で判断せず**該当数を数えた**
- [ ] `honors: none` の項目は 0 点を付けず、**採点対象から外した**
- [ ] 仕様遵守率が高く、該当数が多い場合は §4.1 の4つの兆候を確認した
- [ ] ボーカルの4項目は少なくとも**一度、耳で聴いて確かめた**
- [ ] ★ **耳での比較は最後に行う**。A/B の順序をランダムにする → ペアごとに比較する → **同じペアを2回聴き、結論が一致するか確認する**
- [ ] 2回の結論が一致しない場合は、**差がないと判断し、変更しない**

## 付録：出典

- 実測データ（§2.1 の 62/62、下記の 22% と 5/7）は、Cambridge-MT のマルチトラックから自然抽出した62曲を集計したもの。5/7 は、そのうち7曲のセクション境界を人手で注釈した正解データに基づく
- ゼロ点 63–66 は §3.2 を参照
- このスキルの14項目はすべて人が判定できる
- 14項目のうち、1–5、7–9、11 は音声分析で自動算出でき、**6、10、12、13、14 は人が判定する**

> ★ **測定方法に関する注意**（過去の失敗例）
> 指標が正確に測れないときは、**指標の値から教科書の知見を覆す前に、指標が意図した対象を測っているかを確かめる**。
> たとえば「最大のクライマックスの前にエネルギーがいったん下がる」というルールに該当した割合は、全62曲では 22% だったが、人手で注釈した7曲の正解データでは 5/7 だった。
> アルゴリズムはエネルギーのピークを「最大のクライマックス」とみなすが、人の耳は別の手がかりでも判断する。
> **22% という値では、このルールを測れていない。**
