# コーパス層（Case Studies & Corroboration）

**この層では、次の問いに答える。**

> **教科書に書かれていることは、実際の楽曲でも行われているか？**

本庫では、教科書から採ったルールを**実際のマルチトラック音源62曲で検証した**。
検証結果は3段階に分け、**強いルールだけを20項目のセルフチェックに入れる**。

## 1. コーパスの3原則

### 1.1 ★ 保存するのは構造とパラメータのみ

> **コーパスの各項目には、音源・楽譜・歌詞を含めず、測定値だけを保存する。**

これは著作権上必要であり、分析の目的にも合っている。
**必要なのは、実際の楽曲におけるパラメータの分布だ。**

### 1.2 ★ 曲を選りすぐるより自然抽出を優先する

**コーパスには、選りすぐった曲の代わりに自然抽出した曲を使う。**

> **曲を選ぶと、ルールに当てはまる側へコーパスが偏る。**
> 良い例だと判断して選ぶ曲は、自分がすでに持っている理論に合う例だからだ。
>
> **自然抽出なら、反例も自然に入る。**

そこで、**Cambridge-MT の60曲以上を、選別せず自然抽出したサンプルとして使った**。
MIDI や分離済みトラックのコーパスを別途探す必要もなくなった。当初は音源分離ツールの校正だけに使う予定だったが、実際の個別トラックを使えば校正自体が不要になる。

### 1.3 コーパスの単位は「逆解析 ARR-SPEC」

**音源ごとに、そこから逆算した ARR-SPEC を1件作る。**
この単位を採用したのは、生成時の成果物と**同じフィールドを使う**ためだ。曲構成、楽器が加わる箇所と抜ける箇所、エネルギーカーブを同じ位置に記録するので、裏付け表では形式を変換せず、コーパスの各項目にルールの判定基準をそのまま適用できる。
フィールドの形式と、測定できないことを明示するために意図的に空欄とする項目は §2.1 を参照。

## 2. 逆解析 ARR-SPEC

### 2.1 形式

本庫の実測コーパスは **63件**（Cambridge-MT のマルチトラック60曲 ＋ 中国語圏のポップスの完成音源3曲）。各項目の冒頭で、データの性質を明示している。

```yaml
# 実測 ARR-SPEC（コーパス項目）—— 音源から逆解析して自動生成
# ★ 構造とパラメータのみを保存し、楽譜や歌詞は保存しない。intent / hooks などの TODO 項目は手入力する。
```

★ **`# TODO` や `# 推定値（実測なし）` というコメントに注意。**
これらは、**何が未測定かを明示するための注記**だ。
`intent.one_thing` のような項目は**機械では測れない**ため、無理に埋めれば根拠のない記録になる。

### 2.2 ★ このコーパスで測れる項目と測れない項目

**Cambridge-MT が収録しているのは、ミックス前の個別トラックだ。** 測定できる範囲は次のとおり。

| 測れる項目 | 測れない項目 |
|---|---|
| セクションの境界、小節数 | **DR / ラウドネス**（ミックス前） |
| テンポ | **ステレオの広がり**（ミックス前） |
| エネルギーカーブ、音を引く箇所 | **スペクトル重心の絶対値**（ミックス・マスタリング前） |
| 楽器が加わる箇所と抜ける箇所（実際の個別トラックがある） | プロダクションの質感 |
| グリッドに対するオンセットのずれ | |
| コード（クロマの照合） | |

★ **測定できないルールは明示し、判定を実行しない。**
ルール表では `evidence: unusable_here` と記し、**集計対象から外す**。根拠のない数値を付けてはいけない。

**この検証に使うコーパスは個別トラックで、完成ミックスを含まないため、これらのルールには現時点で数値がない。**

## 3. 正解データとアノテーション

### 3.1 なぜ人手で作った正解データが必要か

アルゴリズムで検出したセクション境界には、**精度に疑問が残る**（ルール表では `no_truth` と記す）。
独立した正解データがなければ、該当率が異常なときに、ルールが成り立っていないのか、アルゴリズムが測り間違えたのかを判別できない。
§5.2 の「閾値をハードコードした結果、該当率が16%まで下がった」事例では、人手で作った正解データによって判定を見直せた。
そこで、複数曲に手作業でアノテーションを付け、正解データとした。校正結果は §3.2 を参照。

### 3.2 ★ 実測で確かめた懸念

ユーザーは「専門家ではないので、境界を正確に付けられないのでは」と心配していた。**実測では次の結果が出た。**

> **人手で付けた境界とアルゴリズムの検出位置のずれの中央値 = 0.0秒。**

★ **結論**：**セクションの境界は、聴いて変化を感じ取れば判断できる。**
専門家でなくても、アノテーションはアルゴリズムの検出位置と一致した。境界を記録するのに専門知識は要らない。
（**記録できるものは区別する**。境界は記録できるが、「このセクションが聴いていて良いか」という好みは正解データにできない。）

**校正結果**：7曲に手作業でアノテーションを付けた。アルゴリズムの一致率は **72%**、ずれの中央値は **0.0 s**。

### 3.3 アノテーションの付け方

波形を表示して再生できるソフトで曲を聴きながら、**各セクションが始まる時刻を秒単位で記録する**。必要なのは主に時刻で、セクション名の記入は任意。
**聴き取れる境界だけを記録し、判断がつかなければ省く**。正解データとして使うため、誤った位置を記録する方が欠測よりも影響が大きい。5曲あれば使える。

**本庫でアノテーション済みの7曲**（Cambridge-MT）：
AMContra_HeartPeripheral、APZX_CyberMower、DigitalHumans_Electrvm、
Forkupines_Semantics、MERCMusic_Knockout、MR1103_Flags、SimonLyn_Copper

## 4. ★ 裏付け表：ルール × コーパス → 該当率 → 分類

### 4.1 裏付けの妥当性を保つ2つの条件

**裏付け表を有効な検証にするには、次の条件を守る。**

| # | 条件 |
|---|---|
| **1** | ★ **判定基準に生成器の定義を流用してはいけない。** 逆解析 ARR-SPEC の `subtraction_events` は、逆解析時に「直前のセクションより >1 dB 低下」を条件として自動入力する。このフィールドで「実際の編曲で音を引く箇所があるか」を検証すると**循環論法**になる。そこで音を引く箇所の判定はすべて、音楽的に意味のある閾値（≥3 dB）を使って **`energy_curve` から直接計算し直し**、**`subtraction_events` は参照しない** |
| **2** | ★ **コーパスで測定できないルールは明示し、判定を実行しない**（§2.2 参照） |

`evidence` の値は次の3つ。

| 値 | 意味 |
|---|---|
| `ok` | このコーパスで検証できる |
| `unusable_here` | このコーパスのデータは検証に適さず、完成ミックスのコーパスが必要 |
| `no_truth` | 正解データがなく（セクション境界など）、判定基準自体の信頼性に疑問が残る |

### 4.2 第1回の結果

| ルール | 該当 | 分類 |
|---|---|---|
| エネルギーカーブには必ず下降する箇所がある | **62/62** | **強いルール** |
| 曲の途中で加わる楽器が必ずある | **59/59** | **強いルール** |
| 少なくとも1つの楽器が曲の終わりより前に抜ける | **59/59** | **強いルール** |
| 全パートをグリッドに厳密に揃えない | **62/62** | **強いルール** |
| 冒頭からすべての楽器を一度に鳴らさない | **54/59** | **強いルール** |
| 曲中で少なくとも1か所、はっきりと音を引く | 36/62 = **70%** | **傾向** |
| 最大の盛り上がりの前にエネルギーをいったん落とす | 全曲 22% ／ 人手による正解データ 5/7 | ★ **結果が食い違うため、手法としてのみ扱う** |
| 最大の盛り上がりで楽器編成が最も密になる | 25/59 = 42% | **保留** |

### 4.3 分類ごとの扱い

| 分類 | skill での書き方 | lint に含めるか |
|---|---|---|
| **強いルール** | 「必須」 | ✅ 必須チェック |
| **傾向** | 「通常はこうする」 | ❌ 「書き上げた後の必須確認リスト」に入れる |
| **手法** | 「こういう方法もある」 | ❌ 診断手順でのみ扱う |
| **保留** | **skill には書かない** | ❌ 裏付け表にのみ記載し、データの追加を待つ |

### 4.4 ルールを追加する手順

1. ルール本体、**実行可能な判定基準**、`evidence` を1項目にまとめる
2. §4.1 の2つの条件を満たすか確認する
3. 自然抽出したコーパス（§1.2）の各曲に判定基準を適用し、該当数を数える
4. 該当率に応じて分類する（§4.3）
5. ★ **結果を先に記録し**（対象コーパス、判定基準、該当数、分類）、その後で仕様やルールを変更する

> **ルールセットにはバージョンがある。**
> ルールセットを変更したら再計測して、変更前後の結果を比較できるようにする。

## 5. ★ ルールとデータが食い違ったとき

**この skill で最も重要な節。**

### 5.1 まず、指標がルールの対象を測っているか確認する

**指標だけを根拠に教科書を否定しない。**

**実例**：「最大の盛り上がりの前にエネルギーをいったん落とす」は、全62曲では **22%** しか該当しなかったが、
人手でアノテーションを付けた正解データ7曲では **5/7** だった。

**差が出た理由**：アルゴリズムは**エネルギーのピーク**を「最大の盛り上がり」として特定するが、**人は耳で聴いて判断する**。
そのため、22% という値が表すのは**エネルギーのピーク前に低下があった割合**であり、ルールへの該当率ではない。

★ **結論**：このルールの有効性は否定せず、強いルールにも格上げせず、**手法として扱う**。

### 5.2 別の実例：閾値のハードコードで該当率が実態より低く出た

裏付けを集計する際、判定基準を**「ダイナミックレンジ12 dB」にハードコード**したため、
ルール ARR-R-012 の該当率が **16%** に下がり、「教科書が間違っている」と報告しかけた。

**反証の方法**：人手でアノテーションを付けた正解データ7曲で測定 → **5/7 = 71%**。
**修正方法**：正規化した 0–10 の尺度で採点し、**dB 値への復元は行わない**。

★ **一般化できる教訓**：**該当率が異常に低いときは、ルールを疑う前に判定基準を見直す。**

### 5.3 裏付け表と lint が確認することの違い

| | 確認すること |
|---|---|
| **裏付け表** | **人が作る曲では一般にそうするか** |
| **20項目のセルフチェック** | **そうしないと AI が作ったように聴こえるか** |

★ **該当率が70%でも、その数字だけで lint のチェック項目を格下げしない。**
ある手法を使う人は70%だけでも、**使わない30%の曲がすべて機械で作ったように聴こえる**ことはあり得る。

## 8. 作業後の必須チェック

- [ ] ルールを引用するときは「教科書にそう書いてある」で済ませず、**根拠の水準**（強いルール／傾向／手法）を添えた
- [ ] 新たに追加した判定基準に**生成器の定義を流用していない**（§4.1 条件1）
- [ ] コーパスで測定できないルールには **`unusable_here` を付け**、根拠のない値は出していない
- [ ] 該当率が異常に低いときは、**まず判定基準を見直した**（§5.2）
- [ ] 裏付け表の該当率**だけで** lint のチェック項目を格下げしていない（§5.3）
- [ ] ルールセットを変更した場合は、**再計測し、今回の結果を記録した**
